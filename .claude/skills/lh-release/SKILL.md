# lh-release

## Purpose

Prepare and publish a LeanHarness release end-to-end through the changesets/action pipeline.

This is a **project-local skill** (`.claude/skills/lh-release/`), not generated by the `lh init` pipeline. It is only for the LeanHarness repository itself.

## Release Pipeline Overview

The release pipeline uses [Changesets](https://github.com/changesets/changesets) with the `changesets/action@v1` GitHub Action:

```
Feature branch (with .changeset/*.md)
  → Push → CI runs
  → Create PR → CI on PR + changeset check
  → Merge PR (rebase) → CI on main
  → changesets/action creates "Version Packages" PR
  → CI on version PR
  → Merge version PR → auto-publish to npm + GitHub Release
```

## Prerequisites

- Git repository with a `main` branch
- `changesets` configured in the project
- `gh` CLI authenticated and available (`gh auth status`)
- Clean working tree (no uncommitted changes)
- `NPM_TOKEN` configured in GitHub repository secrets

## Steps

### Step 1: Validate Environment

Run:

```bash
npm run build && npm run typecheck && npm test
```

Then:

```bash
git status               # must be clean
gh auth status           # must be authenticated
```

If any check fails, report the issue and do not proceed.

### Step 2: Fetch Latest Main

```bash
git fetch origin main
```

### Step 3: Analyze Commits Since Main

```bash
git log origin/main..HEAD --oneline
git diff --stat origin/main
```

Read `CHANGELOG.md` for current state and last release version.

### Step 4: Determine Recommended Version

Based on commit analysis:

- **patch** (recommended) — bug fixes, patches, docs, internal refactors
- **minor** — new features, backward-compatible changes
- **major** — breaking changes, architectural changes

Look for: `BREAKING CHANGE:` → major, `feat:` → minor, `fix:`/`chore:`/`docs:` → patch.

### Step 5: Ask User for Version

Present the analysis. Use `AskUserQuestion` tool:

```json
{
  "header": "Version bump",
  "question": "Which version should this release be?",
  "options": [
    { "label": "patch (Recommended)", "description": "Bug fixes, docs, internal changes" },
    { "label": "minor", "description": "New features, backward-compatible changes" },
    { "label": "major", "description": "Breaking API or architectural changes" }
  ]
}
```

### Step 6: Run Changeset

```bash
npm run changeset
```

Follow the CLI prompts. If no changesets exist, inform the user and abort.

### Step 7: Commit and Push

```bash
git add .changeset/
git commit -m "chore: add changeset"
git push origin HEAD
```

### Step 8: Create Pull Request

```bash
gh pr create --base main --title "Release v<VERSION>" --body "$(generate_pr_body)"
```

Use the PR template at the bottom of this document.

### Step 9: Wait for CI on PR

```bash
gh pr checks --watch
```

Required checks (from `.github/workflows/ci.yml`):
- Build & Test (Node 22 and 24)
- Changeset Check

Do NOT proceed with failing checks.

### Step 10: Merge PR (Rebase)

```bash
gh pr merge --rebase --delete-branch
```

**Always use `--rebase`** — do NOT squash or merge-commit. Changeset files must remain in the commit graph.

### Step 11: Wait for CI on Main

```bash
gh run list --branch main --limit 5
gh run watch <run-id>
```

### Step 12: Monitor for Version Packages PR

After main CI passes, `changesets/action@v1` (`.github/workflows/release.yml`) automatically creates/updates a **"Version Packages" PR**.

Monitor:

```bash
gh pr list --search "Version Packages" --state open
```

### Step 13: Check Version Packages PR

```bash
gh pr view <version-pr-number>
```

Verify:
- `package.json` version bump is correct
- `CHANGELOG.md` entry is accurate
- Changeset files consumed (deleted from `.changeset/`)

### Step 14: Wait for CI on Version PR

```bash
gh pr checks <version-pr-number> --watch
```

### Step 15: Merge Version PR

```bash
gh pr merge <version-pr-number> --rebase --delete-branch
```

Merging triggers the `changesets/action` workflow on main, which automatically:
- Creates a git tag
- Creates a GitHub Release with release notes
- Publishes to npm via `NPM_TOKEN`

### Step 16: Verify Release

```bash
npm info @feneto/lh version
```

```bash
gh release list --limit 3
```

Confirm version matches, npm package and GitHub Release are live.

## PR Template

```
## Release Summary

[Generated from changeset]

## Changes

[Bullet list of changes from changeset]

## Checklist

- [ ] Tests pass
- [ ] Typecheck passes
- [ ] Lint passes
- [ ] Documentation updated (if applicable)
- [ ] CHANGELOG updated
```

If `.github/PULL_REQUEST_TEMPLATE.md` exists, use it and append release notes.

## Error Handling

- **No changesets generated**: No version bump needed.
- **Git conflicts**: Re-fetch and rebase. `git fetch origin main && git rebase origin/main`.
- **PR creation fails**: Report error, provide manual PR link.
- **gh not authenticated**: Prompt user to `gh auth login`.
- **CI fails**: Do NOT proceed. Fix, amend, re-push.
- **Version Packages PR not created**: Check `NPM_TOKEN` secret and GitHub Action permissions in `.github/workflows/release.yml`.

## Rules

- Do not proceed if working tree is not clean.
- Always run `npm run build && npm run typecheck && npm test` before creating a changeset.
- Do not force-push during release.
- Preserve all changeset content exactly as generated.
- **Never skip CI waiting steps**.
- **Always use `--rebase` for merges** — squash and merge-commit destroy changeset files.
- This is an internal LeanHarness project skill. It is NOT shipped to end users.
